# Standardized OpenAPI Security Responses

Implement annotation-aware OpenAPI documentation for secured controller operations. The shared
configuration must add the standard `ApiErrorResponse` contract for `401 Unauthorized` and `403
Forbidden` whenever a controller method or controller class uses `@PreAuthorize`, preserve every
explicit operation response, and avoid claiming that public endpoints are secured. Validate the
change across every current `service-web` consumer, and remove permission-service's now-redundant
explicit `403` responses. Keep the repositories on their checked-in `0.0.17-SNAPSHOT` dependency
version; release versioning and publication to a remote repository are outside this plan.

## Phase 1: Implement Shared Annotation-Aware Security Responses

### Workspace

.

### Goal

Make `BaseOpenApiConfig` the canonical source for standard `401` and `403` OpenAPI responses on
`@PreAuthorize` operations while preserving consumer-owned response documentation.

### Scope

- Add a SpringDoc `OperationCustomizer` that recognizes merged `@PreAuthorize` annotations on
  controller methods and controller classes.
- Add standard `401` and `403` responses using the shared `ApiErrorResponse` schema and examples
  that match the runtime security response writers.
- Make all shared default responses additive so explicit controller responses win for `400`, `401`,
  `403`, `404`, `500`, and `503`.
- Add focused tests for annotation detection, response content, and explicit-response preservation.
- Update the shared OpenAPI documentation and the relevant `AGENTS.md` orientation text.
- Publish the verified snapshot to Maven Local for the consumer phases.

### Non-goals

- Do not change runtime authentication or authorization behavior.
- Do not parse `@PreAuthorize` expressions or document the required authority value in OpenAPI.
- Do not add security responses to every operation unconditionally.
- Do not infer security from service-specific `SecurityFilterChain` or `SecurityWebFilterChain`
  path matchers.
- Do not introduce an OpenAPI security scheme for the trusted internal claims headers.
- Do not change artifact versions or publish to GitHub Packages.

- `service-web/src/main/java/org/budgetanalyzer/service/security/ClaimsHeaderSecurityConfig.java`
- `service-web/src/main/java/org/budgetanalyzer/service/security/ReactiveClaimsHeaderSecurityConfig.java`
- `service-web/src/main/java/org/budgetanalyzer/service/security/ClaimsHeaderSecurityErrorResponseWriter.java`
- `service-web/src/main/java/org/budgetanalyzer/service/security/ReactiveClaimsHeaderSecurityErrorResponseWriter.java`
- `service-web/src/test/java/org/budgetanalyzer/service/config/BaseOpenApiConfigTest.java`

### Execution steps

1. Confirm the service-common worktree has no overlapping user changes. Re-run discovery for
   `BaseOpenApiConfig`, its tests, current consumers, and their `@PreAuthorize` usage rather than
   relying solely on this plan's inventory.
2. Extend `BaseOpenApiConfigTest` first with real `HandlerMethod` fixtures for method-level,
   class-level, and unsecured controller methods. Cover merged annotation lookup without Mockito or
   application-owned bean mocks.
3. Add test cases proving secured operations receive both `401` and `403`, unsecured operations
   receive neither, examples use `ApiErrorType.UNAUTHORIZED` and `ApiErrorType.FORBIDDEN`, and an
   existing explicit response object and description remain unchanged.
4. Add an inherited `@Bean` of type `OperationCustomizer` to `BaseOpenApiConfig`. Detect
   `@PreAuthorize` on the handler method or bean type using Spring's merged-annotation facilities,
   then add the standard security responses only for matching handlers.
5. Extend the HTTP-status-to-error-type mapping for `UNAUTHORIZED` and `FORBIDDEN`. Use the runtime
   messages `Authentication required` and `You do not have permission to perform this action` in
   shared examples so generated documentation matches servlet and reactive behavior.
6. Introduce or reuse one small helper that adds a generated response only when that status code is
   absent. Apply that behavior to every response generated by the base configuration so endpoint
   annotations retain their specialized descriptions, schemas, headers, and examples.
7. Keep the existing generic `OpenApiCustomizer` responsible for HTTP-method defaults and the new
   `OperationCustomizer` responsible for handler-annotation-aware security defaults. Do not attempt
   to recover handler metadata from the completed `OpenAPI` path tree.
8. Update class and method Javadocs, `docs/spring-boot-conventions.md`, and the nearest relevant
   `AGENTS.md` OpenAPI descriptions. Document that shared `401`/`403` responses are generated for
   `@PreAuthorize` operations, explicit responses take precedence, and public or service-specific
   authentication flows remain explicitly documented by their owner.
9. Run the focused test class, inspect failures, and fix the implementation rather than weakening
   existing assertions.
10. Run the repository's required formatting and build commands in sequence, inspect Checkstyle
    output, and publish the successful `0.0.17-SNAPSHOT` artifacts to Maven Local for later phases.

### Implementation notes

- SpringDoc 2.9.1 exposes `OperationCustomizer#customize(Operation, HandlerMethod)`, which is the
  appropriate boundary for controller annotation inspection.
- `@PreAuthorize` supports method and type targets. Annotation detection must account for composed
  and inherited annotations through merged lookup rather than direct `getAnnotation` calls.
- Do not overwrite an operation response that SpringDoc already built from `@ApiResponse`. This is
  necessary for permission-service's specialized `503` text and Session Gateway's service-specific
  `401` semantics, in addition to future explicit overrides.
- Adding generated documentation is backwards compatible. Keep the current snapshot version for
  local lockstep verification; a later release process can decide the next published version.

Confirm the Maven Local publication contains `org.budgetanalyzer:service-web:0.0.17-SNAPSHOT` before
starting a consumer phase.

### Completion criteria

- Shared tests prove method-level and class-level `@PreAuthorize` operations receive correct `401`
  and `403` documentation and unsecured methods do not.
- Shared defaults preserve all explicitly documented responses.
- The generated examples reference `ApiErrorResponse` and use the correct authorization error
  types and runtime messages.
- Shared Javadocs and durable OpenAPI guidance describe the behavior and ownership boundary.
- The required service-common build passes and the updated snapshot is available in Maven Local.

   repositories.
2. Add one full-context MockMvc OpenAPI integration test method using the repository's real Spring
   beans and existing integration-test support. Read `/permission-service/v3/api-docs` once with
   the matching context path and parse it with the real `ObjectMapper`.
3. Assert that `GET /v1/users`, `GET /v1/users/{id}`, and `POST
   /v1/users/{id}/deactivate` each contain `401` and `403` responses whose JSON schemas reference

### Implementation notes

- Keep explicit response documentation when it carries endpoint-specific meaning. The cleanup is
  limited to standard `403 Insufficient permissions` entries now owned by service-common.
- The internal endpoint is intentionally the negative case because it has no `@PreAuthorize` and
  is admitted by the narrow `/internal/v1/users/*/permissions` security matcher.
- Prefer a focused `PermissionOpenApiIntegrationTest` over adding unrelated OpenAPI assertions to
  behavior-oriented controller tests.
